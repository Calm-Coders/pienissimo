Technical design review · 26 August 2026

A smaller skill with stronger evidence

Redesign org-status-check as an orchestrator over deterministic collectors. Use Graphify and the code index to narrow investigation—not to prove deployed state.

Recommended: hybrid pipeline One structured three-way comparison, two optional intelligence aids, and publication separated from the audit itself.

Observed failure

Field existence was misread

User-level describe hid OrderItem.Tranche__c. The field was deployed but granted to nobody. FieldDefinition is the existence authority; FieldPermissions answers usability.

Index boundary

Graphify is not an exact inventory

Two source fields share the API name Tranche__c, while the current graph exposes one field node. That is fine for navigation, unsafe as the canonical diff key.

Validation gap

Build-state references can drift

The register contains build-state refs such as QUO-01 and QUO-06 without matching requirement IDs. The current vault check validates tracked_by, not build-state refs.

Target architecture

Three authorities in, one evidence matrix out

Precision model

Replace one overloaded verdict with three independent axes

Axis 1

Requirement compliance

Matches · partial · divergent · missing · unverifiable

Axis 2

Deployment drift

Aligned · repository-only · org-only · content mismatch

Axis 3

Operability

Usable · permission-blocked · unconfigured · uncovered · unproven

Why this matters: OrderItem.Tranche__c is not “missing.” It is present and aligned, while its operability is permission-blocked and its behavior is unimplemented.

Why shared project resources?

This repository mirrors skills under .agents and .claude. Keeping scripts and detailed references at project level avoids duplicating implementation while both clients retain a discoverable SKILL.md.

Why a verification sidecar?

It maps requirement IDs to component assertions without rewriting the contract-bound requirement text. Expected values should reference structured paths in the register where possible, not duplicate them.

Why a generated cache?

A timestamped snapshot supports delta runs and reproducible evidence. Store schemas, names, hashes, counts, and status distributions—never credentials, catalogue values, or personal records.

Recommended SKILL.md workflow

Eight decisions, not hundreds of ad hoc searches

1

Select scope and side effects

Targeted or full; report, reconcile, or publish. Natural-language status questions default to targeted/report.

2

Preflight

Confirm UAT alias and org ID, branch, working tree, previous watermark, Graphify health, and optional code-index health.

3

Build the checklist

Resolve machine-checkable assertions; mark unmapped or behavioral requirements unverifiable rather than guessing.

4

Collect two exact snapshots

Parse repository XML directly. Query the live org with JSON output, FieldDefinition, FieldPermissions, coverage, and scoped aggregate checks.

5

Compare deterministically

Generate compliance, drift, and operability axes using canonical keys such as field:OrderItem.Tranche__c.

6

Investigate exceptions

Use Graphify for Salesforce dependency context and the code index for code paths. Verify every lead against metadata or source.

7

Produce only the requested output

Report by default. Reconcile repository records or publish external mirrors only in the matching mode.

8

Validate invariants

No org writes, no force-app changes, valid refs, permitted file diff, vault check, formatting, and public leak check when publishing.

Implementation sequence

Build the safety rails before the automation

Phase 1

Refactor instructions

Introduce scope/output modes, evidence authority, FLS-safe field checks, index degradation, and remove the stale hardcoded date.

Phase 2

Add snapshot + validator

Normalize JSON, canonical keys, provenance, requirement-ref validation, and fixtures for known failures.

Phase 3

Add deterministic diff

Automate structural verdicts and produce the evidence matrix. Leave behavior and ambiguity to targeted review.

Phase 4

Reduce rendering churn

Generate affected sections from structured results and enforce a changed-file allowlist and diff-size warning.

Phase 5

Forward-test

Run read-only fixtures and a live UAT audit; verify no source or org mutation and no repeated false negatives.

Phase 6

Propagate

Synchronize the .agents/.claude copies and update the start-sf-projects templates only after the Pienissimo version proves stable.

Acceptance tests

Failures the redesigned skill must survive

  • Field exists but has zero human FLS grants → present + permission-blocked.
  • Same field API name on two objects → two independent canonical keys.
  • Repository-only and org-only components → drift classified separately.
  • Picklist changed while records retain inactive values → configured + data-divergent.
  • Code index unavailable → rg fallback, no blocked audit.
  • Live org unavailable → repository-only report, no status mutation.
  • Unknown requirement/build-state ref → validation failure.
  • Publish mode → public leak check passes and Notion is re-fetched after write.
